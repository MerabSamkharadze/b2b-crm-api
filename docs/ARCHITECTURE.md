# არქიტექტურა

ეს დოკუმენტი აღწერს, **როგორ მოგზაურობს request-ი** სისტემაში და რატომ
არის კოდი ასე დაწყობილი.

---

## 1. Request-ის სრული გზა

```
   HTTP Request
        │
        ▼
┌───────────────────┐
│  Middleware       │  helmet() — უსაფრთხოების header-ები
│                   │  CORS      — რომელ origin-ს ვემსახურებით
└─────────┬─────────┘  (main.ts → configureApp)
          ▼
┌───────────────────┐
│  Guards           │  1. JwtAuthGuard  — token ვალიდურია? → request.user
│  (APP_GUARD)      │  2. RolesGuard    — @Roles-ის როლი აკმაყოფილებს?
└─────────┬─────────┘  ❗️ რიგითობა = app.module.ts providers-ის რიგითობა
          ▼
┌───────────────────┐
│  Interceptors     │  LoggingInterceptor — x-request-id + ხანგრძლივობა
│  (APP_INTERCEPTOR)│  (აქვს წვდომა request-ის დასრულების მომენტზეც)
└─────────┬─────────┘
          ▼
┌───────────────────┐
│  Pipes            │  ValidationPipe — DTO-ს class-validator წესები
│                   │  ParseUUIDPipe  — :id ნამდვილი UUID-ია?
└─────────┬─────────┘  ❌ არასწორი მონაცემი აქ იჭრება 400-ით
          ▼
┌───────────────────┐
│  Controller       │  მხოლოდ: მიიღე → გადაეცი service-ს → დააბრუნე
│                   │  ბიზნეს ლოგიკა აქ **არ** იწერება
└─────────┬─────────┘
          ▼
┌───────────────────┐
│  Service          │  ბიზნეს ლოგიკა + ავტორიზაციის row-level ფენა
│                   │  (ownerScope → Prisma-ს where)
└─────────┬─────────┘
          ▼
┌───────────────────┐
│  PrismaService    │  extends PrismaClient
│                   │  driver adapter (@prisma/adapter-pg) → node-postgres
└─────────┬─────────┘
          ▼
    PostgreSQL 16
```

პასუხი იმავე გზით ბრუნდება უკან. თუ გზაში exception მოხდა:

```
  Exception → ExceptionFilter → HTTP პასუხი
              PrismaExceptionFilter: P2002 → 409, P2025 → 404, P2034 → 409
```

**სცადე თვითონ:** გაუშვი `npm run start:dev` და ნახე ტერმინალში —
ყოველ request-ზე დაინახავ `LoggingInterceptor`-ის ხაზს და Prisma-ს
დაგენერირებულ SQL-ს (`log: ['query']` development-ში ჩართულია).

## 2. Module-ების გრაფი

```
                    AppModule
                        │
    ┌───────────────────┼────────────────────────────┐
    │                   │                            │
ConfigModule      PrismaModule (@Global)      ThrottlerModule
(isGlobal)         └─ PrismaService ──────────────┐
                                                  │ ყველგან ხელმისაწვდომია
    ┌─────────────────────────────────────────────┤
    │                                             │
AuthModule ──imports──> UsersModule          CompaniesModule
  ├─ JwtStrategy          └─ UsersService     ContactsModule
  ├─ JwtAuthGuard  ─┐                         DealsModule
  ├─ RolesGuard   ──┤ APP_GUARD-ით            ActivitiesModule
  └─ AuthService    │ გლობალურად               DashboardModule
                    │ რეგისტრირებული           HealthModule
                    ▼
            ყველა route დაცულია by default
```

### დამოკიდებულების ოქროს წესი

```
AuthModule  →  UsersModule     ✅  (ერთი მიმართულება)
UsersModule →  AuthModule      ❌  (არასდროს)
```

ამიტომ `forwardRef()` არსად არ გვჭირდება. როცა circular dependency გჩნდება,
ეს თითქმის ყოველთვის ნიშნავს, რომ პასუხისმგებლობები არასწორად გაიყო.

**რატომ არ სჭირდება CRM module-ებს AuthModule-ის იმპორტი?** იმიტომ რომ
`JwtAuthGuard` და `RolesGuard` `APP_GUARD`-ით არის რეგისტრირებული
`AppModule`-ში — ანუ ისინი ყველა route-ზე მუშაობენ ავტომატურად.
`@Roles()` და `@CurrentUser()` კი უბრალო დეკორატორებია (metadata), და
არა provider-ები — ამიტომ მათი იმპორტი DI-ს არ ეხება.

## 3. <a id="schema"></a>რელაციური დიზაინი — რატომ ასე

### Cascade-ების ასიმეტრია

| რელაცია                     | წესი         | რატომ                                                                                                                                      |
| --------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `Company.owner → User`      | **Restrict** | მომხმარებლის წაშლა იბლოკება, სანამ მას კლიენტები ეკუთვნის. CRM-ში "ვის ეკუთვნის კლიენტი" ფინანსური ინფორმაციაა — ჯერ reassign, მერე წაშლა. |
| `Contact.company → Company` | **Cascade**  | კონტაქტი კომპანიის გარეშე აზრს კარგავს.                                                                                                    |
| `Deal.company → Company`    | **Restrict** | ⚠️ შეგნებულად **განსხვავებული** Contact-ისგან: შემოსავლის ისტორია კომპანიის "დასუფთავებას" უნდა გადაურჩეს.                                 |
| `Deal.contact → Contact`    | **SetNull**  | ადამიანმა სამსახური შეიცვალა — გარიგება რჩება. (Prisma მოითხოვს, რომ ველი optional იყოს.)                                                  |
| `User.manager → User`       | **SetNull**  | მენეჯერის წაშლა არ უნდა დაბლოკოს ან დააქციოს ქვეშევრდომები.                                                                                |
| `DealStageHistory.deal`     | **Cascade**  | აუდიტი კონკრეტულ გარიგებას ეკუთვნის.                                                                                                       |
| `Activity.owner → User`     | **Restrict** | აუდიტის კვალი ავტორთან ერთად არ უნდა გაქრეს.                                                                                               |

პრაქტიკული შედეგი: `DELETE /companies/:id` გარიგებებიან კომპანიაზე
დააბრუნებს **409 Conflict**-ს (P2003), და არა ჩუმად წაშლას.

### ინდექსები

**Prisma PostgreSQL-ზე foreign key-ებზე ინდექსს ავტომატურად არ აკეთებს**
(MySQL-ზე აკეთებს). ამიტომ ყველა FK, რომლითაც ვფილტრავთ, ხელით არის
დაინდექსებული — იხ. `schema.prisma`-ს `@@index` ხაზები.

`role`-ზე ინდექსი შეგნებულად **არ** გვაქვს: 3 განსხვავებული მნიშვნელობა
(დაბალი selectivity) ნიშნავს, რომ PostgreSQL ინდექსს მაინც არ გამოიყენებს.

### ფული

`amount Decimal @db.Decimal(12,2)` — **არასდროს Float**.
`0.1 + 0.2 === 0.30000000000000004` ფინანსურ ანგარიშში დაუშვებელია.

API-ში თანხა **string-ად** მიდის და ბრუნდება (`"15000.00"`):

- შემოსვლაზე: JSON-ის number კლიენტის მხარეს უკვე კარგავს სიზუსტეს
- გასვლაზე: `toDealResponse()` აკეთებს `toFixed(2)`-ს, რადგან Prisma-ს
  Decimal-ის default სერიალიზაცია `"15000.5"`-ს იძლევა (არასტაბილური ათწილადები)

## 4. <a id="rbac"></a>RBAC — ორფენოვანი ავტორიზაცია

```
ფენა 1: Guard      "შეგიძლია ამ ღილაკზე დაჭერა?"   → @Roles(Role.ADMIN)
ფენა 2: where      "რომელ სტრიქონებს ხედავ?"        → ownerScope(actor)
```

ეს გაყოფა არსებითია: **Guard-ს SQL-ის გადაწერა არ შეუძლია.** მას მხოლოდ
"დიახ/არა" შეუძლია. row-level ფილტრაცია query-ის ნაწილია.

### ownerScope — სუფთა ფუნქცია

```ts
where: {
  AND: [ownerScope(actor), buildFilters(query)];
}
```

⚠️ `AND` და არა spread. `{ ...ownerScope(actor), ...filters }` სახიფათოა:
თუ ფილტრებშიც `ownerId` აღმოჩნდა, ის **გადააწერს** scope-ს და
უსაფრთხოება ჩამოინგრევა.

### რატომ არა სხვა მიდგომები

| მიდგომა                                 | რატომ არ ავირჩიეთ                                                                                                                                                                                                                                                                                        |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Prisma `$extends`** (query extension) | fail-closed და DRY, მაგრამ: სჭირდება request-scoped კონტექსტი (AsyncLocalStorage/CLS), `$extends` **ახალ ტიპს** აბრუნებს — ანუ `PrismaService extends PrismaClient` ტიპებს ამტვრევს, და მწვავე კუთხეები აქვს `upsert`/nested write/`groupBy`-ზე. მთავარი მინუსი სწავლისთვის: **მექანიზმს უხილავს ხდის.** |
| **Guard / Interceptor**                 | არასწორი ფენაა. Guard-ი id-ით წაკითხვისას იძულებული იქნება ჯერ წაიკითხოს, მერე შეამოწმოს (ზედმეტი query + 403/404-ის გაჟონვის დილემა).                                                                                                                                                                   |
| **CASL / policy objects**               | სწორი არჩევანი, როცა უფლებები რთულდება ("თავისი ხარჯის დამტკიცება არ შეიძლება"). ჩვენი სამი როლისთვის ზედმეტი სირთულეა.                                                                                                                                                                                  |

### ჩაწერის შეზღუდვა — "დავიწყებული ნახევარი"

```ts
prisma.deal.update({ where: scopedWhereUnique(id, actor), data });
```

Prisma-ს `extendedWhereUnique` საშუალებას გვაძლევს `where`-ში id-ის გარდა
სხვა პირობებიც ჩავწეროთ. სხვისი ჩანაწერზე Prisma აგდებს **P2025**-ს →
`PrismaExceptionFilter` → **404**.

**რატომ 404 და არა 403:** 403 ("უფლება არ გაქვს") ადასტურებს, რომ ჩანაწერი
არსებობს. თავდამსხმელს id-ების გადარჩევით შეუძლია ბაზის შიგთავსის რუკა
ააგოს. 404 არაფერს ამბობს.

### JWT-ის შემადგენლობა

payload-ში **მხოლოდ `sub`** (მომხმარებლის id) წერია. role და გუნდი
ყოველ request-ზე ბაზიდან იკითხება (`JwtStrategy.validate`).

|                         | stateless (role token-ში) | ჩვენი არჩევანი (role ბაზიდან) |
| ----------------------- | ------------------------- | ----------------------------- |
| სისწრაფე                | ბაზას არ მიმართავს        | +1 SELECT თითო request-ზე     |
| უფლებების გაუქმება      | 15 წუთი დაგვიანებით       | მყისიერად                     |
| დეაქტივირებული ანგარიში | კიდევ მუშაობს             | მაშინვე 401                   |

ჩვენ სისწრაფე გავცვალეთ კონტროლზე. ეს შეგნებული არჩევანია და არა
დაუდევრობა — იხ. `docs/DECISIONS.md`.

## 5. ჯერ არ არის გაკეთებული (და რატომ)

| რამ                                    | კომენტარი                                                                                                                           |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Soft delete (`deletedAt`)              | v1-ში hard delete-ია; `Restrict` წესები ისედაც იცავს საშიშ შემთხვევებს. გლობალური ფილტრი Prisma `$extends`-ით — მომავალი სავარჯიშო. |
| Refresh token მრავალი მოწყობილობისთვის | ერთი `hashedRefreshToken` სვეტი = ერთი session. მრავალისთვის ცალკე `RefreshToken` ცხრილი სჭირდება.                                  |
| Rate limit განაწილებული                | ThrottlerModule-ის მეხსიერების storage ერთ instance-ზე მუშაობს. production-ში Redis.                                                |
| Multi-tenancy (`organizationId`)       | ყველა ცხრილს სჭირდებოდა + scope-ში ჩაწერა. შემდგომში დამატება მტკივნეულია — ამიტომ გადაწყვეტილება ცნობიერად არის დაფიქსირებული.     |
| Observability (OpenTelemetry)          | `LoggingInterceptor`-ის `x-request-id` არის მინიმალური საფუძველი.                                                                   |
| CI (GitHub Actions)                    | `npm run lint && npm test && npx prisma validate` — სამი ხაზი.                                                                      |
